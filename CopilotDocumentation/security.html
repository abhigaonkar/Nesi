🔐 NESI Security & Authentication

Security Overview

NESI implements a comprehensive multi-layered security architecture that protects sensitive business data through OAuth 2.0 authentication, role-based authorization, and granular access controls. The system supports three distinct user types (Employee, Customer, Vendor) with customizable permission structures at page, privilege, and role levels.

🔑 OAuth 2.0 Bearer Token Authentication

Authentication Flow

NESI uses OAuth 2.0 Bearer Token authentication implemented via Microsoft OWIN middleware. The authentication process follows these steps:

  1. Client Request: User submits credentials (username/password) to /token endpoint
  2. Credential Validation: NesiAuthorizationServerProvider validates credentials against the database
  3. Token Generation: Upon successful authentication, OAuth server generates access token and refresh token
  4. Token Response: Tokens returned to client with expiration time
  5. API Access: Client includes Bearer token in Authorization header for subsequent API requests
  6. Token Validation: Each API request validates the Bearer token before processing
  7. Token Refresh: Client can use refresh token to obtain new access token without re-authentication

Authentication Provider Implementation

// NesiAuthorizationServerProvider.cs public override async Task GrantResourceOwnerCredentials( OAuthGrantResourceOwnerCredentialsContext context) { using (var repo = new AuthRepository()) { var user = repo.FindUser( context.UserName, context.Password, context.Request.RemoteIpAddress ); if (user == null) { context.Rejected(); context.SetError("invalid_grant", "Invalid username/password"); } else { var ticket = CreateTicket(user, context.Options.AuthenticationType); context.Validated(ticket); } } }

Access Level: Full System

Internal employees with role-based permissions to all business functions including CRM, quotes, work orders, purchasing, time tracking, and administrative tools.

  • Privilege-based controls
  • Business unit filtering

🛡️ Multi-Level Authorization

1. Page-Level Authorization

PageAuthorizationFilterAttribute enforces access control at the controller/page level. Each controller is decorated with a specific page ID, and the filter validates that the current user has authorization to access that page.

[PageAuthorizationFilter(PageId = 123)] public class CustomerController : ApiController { // Page authorization checked before any action executes }

Implementation: Checks user.AuthorizePage(PageId) against UserPageAuth table

2. Privilege-Level Authorization

PrivilegeAuthorizationFilterAttribute provides fine-grained control over specific actions within a page. Even if a user has page access, they may need additional privileges for sensitive operations (create, edit, delete, approve, etc.).

[PrivilegeAuthorizationFilter(PrivilegeId = 456)] public IHttpActionResult DeleteCustomer(int id) { // Privilege authorization for delete operations }

Implementation: Checks user.AuthorizePrivilege(PrivilegeId) against UserPrivAuth table

3. Role-Based Authorization

Users are assigned to one or more roles (Administrator, Manager, Sales, Technician, etc.). Roles define collections of pages and privileges that can be assigned to users as a group.

Role Typical Permissions Common Users
Administrator Full system access, user management, configuration IT Staff, System Admins
Manager Approve quotes, manage work orders, view reports Department Managers, Supervisors
Sales Customer management, quote creation, sales reports Sales Representatives
Project Manager Work order management, resource allocation, scheduling Project Managers
Technician Timesheet entry, work order viewing, expense tracking Field Technicians, Engineers
Accounting Financial reports, invoicing, AR/AP management Accounting Staff

4. Business Unit Filtering

Beyond page and privilege authorization, NESI implements data-level security through business unit filtering. Users are assigned to specific business units and can only access data associated with their authorized units.

  • FilterBusinessUnit: Automatically filters queries by user's business unit assignments
  • Multi-Unit Access: Users can be assigned to multiple business units
  • Data Segregation: Ensures users cannot access data outside their authorized scope
  • API-Level Filtering: Applied at data access layer, not just UI

Password Storage

Passwords are stored using cryptographic hashing algorithms (BCrypt or similar). Plain-text passwords are never stored in the database. Password verification compares hashes rather than plain-text values.

⏱️ Session Management

Session Configuration

Setting Value Purpose
Session Timeout 1440 minutes (24 hours) Extended timeout for long-running operations
Token Storage Client-side (LocalStorage/SessionStorage) Bearer token cached for API requests
Session State Stateless (token-based) No server-side session storage required
Concurrent Sessions Allowed Users can be logged in from multiple devices
Session Tracking Global.OnlineUser cache Track active users for real-time features

User Session Lifecycle

  1. Login: User authenticates and receives Bearer token
  2. Token Caching: Token stored in client (LocalStorage or SessionStorage)
  3. Active Session: User tracked in Global.OnlineUser dictionary with unique GUID
  4. API Requests: Each request includes Bearer token in Authorization header
  5. Token Validation: OWIN middleware validates token on each request
  6. Token Refresh: Client can refresh expired tokens using refresh token
  7. Logout: Client discards tokens, server removes from OnlineUser cache

Passport-Based Authentication

NESI supports a passport-based authentication mechanism for user switching and special authentication scenarios. Administrators can generate secure passports to log in as another user for support or testing purposes.

// Grant type: "passport" // Parameters: passport_hash (encrypted passport ID) public override async Task GrantCustomExtension(OAuthGrantCustomExtensionContext context) { var passportId = context.Parameters["passport_hash"]; var passport = new passport(passportId); if (passport.check()) { var user = repo.FindUser(passport.to_member_id); context.Validated(CreateTicket(user, context.Options.AuthenticationType)); } }

Audit Trail Features

  • IP Address Logging: All authentication attempts log client IP address
  • User Agent Tracking: Browser and device information captured
  • Action Logging: CRUD operations on sensitive data are logged
  • Change History: Before/after values for critical data changes
  • Retention Policy: Audit logs retained per compliance requirements
  • Tamper-Proof: Audit logs are insert-only with no update/delete permissions
  • Reporting: Audit reports available for security review and compliance

🚨 Security Best Practices Implemented

🔐 HTTPS Enforcement

Production deployment requires HTTPS for all communications. OAuth tokens transmitted only over encrypted connections.

🛡️ CORS Configuration

Cross-Origin Resource Sharing (CORS) configured to allow specific origins for API access.

🔒 SQL Injection Prevention

Entity Framework with parameterized queries prevents SQL injection attacks.

🚫 XSS Protection

Input validation and output encoding prevent cross-site scripting attacks.

⚡ Rate Limiting

API rate limiting prevents brute force attacks and denial of service.

📊 Error Handling

Secure error messages prevent information disclosure while logging detailed errors server-side.

🔍 Security Monitoring & Alerting

Active Monitoring

  • Failed Login Monitoring: Alerts on excessive failed login attempts
  • Unusual Access Patterns: Detection of abnormal user behavior
  • Privilege Escalation: Monitoring for unauthorized privilege changes
  • After-Hours Access: Alerts for access outside normal business hours
  • Data Export Monitoring: Tracking of large data exports or unusual queries

⚠️ Security Considerations

  • Regularly review and update user permissions
  • Enforce strong password policies organization-wide
  • Monitor audit logs for suspicious activity
  • Keep OAuth token expiration times appropriate for your security requirements
  • Implement network-level security (VPN, firewall rules) for external access
  • Regular security assessments and penetration testing recommended
